# Правила работы с shared

Эти правила действуют для изменений `shared`, а также для серверного API и клиентского кода, использующего общую библиотеку.

## Назначение и зависимости

- `:shared` — единый источник сетевых моделей, путей API, имён параметров и HTTP-запросов между сервером и клиентами.
- Общий код размещается в `shared/src/commonMain/kotlin/com/onebook/shared/api`. Он должен работать на Android и JVM.
- `server` и `client/core/data` подключают библиотеку через `implementation(project(":shared"))`. `shared` не зависит от модулей сервера или клиента.
- В `shared` находятся сериализуемые DTO, `ApiRoutes` и `OneBookApi`. UI, ViewModel, DI, кеш, БД, парсеры провайдеров, файловое хранилище и бизнес-сценарии остаются в своих модулях.
- Доменные модели клиента и сервера остаются отдельными от DTO. Клиент преобразует DTO в `core/data`, сервер — на границе `api`. Клиентский `core/domain` и фичи не зависят от `shared` и не используют сетевые DTO.
- Серверные поля хранения, например путь к локальному аудиофайлу, не добавляются в публичные DTO без потребности API.

## Модели и совместимость

- Модели тел запросов, ответов и ошибок объявляются в `shared` с `@Serializable`. Не создавай их копии в сервере или клиенте.
- Для одинакового формата запроса и ответа можно использовать один DTO, как `PositionDto`. Если форматы различаются, объявляй отдельные модели.
- Сохраняй существующие JSON-имена, типы и смысл полей. Новые поля, которые могут отсутствовать в ответах старого сервера или сохранённом кеше, должны иметь подходящее значение по умолчанию.
- Переименование Kotlin-свойства не должно случайно менять JSON-контракт: при необходимости сохраняй сетевое имя через `@SerialName`.
- При изменении контракта учитывай разные версии клиента и сервера и уже записанные JSON-снимки в кеше. Для несовместимого изменения явно описывай переход и обновляй обе стороны, тесты и документацию.
- Проверка бизнес-правил выполняется на сервере, даже если клиент также проверяет ввод.

## Маршруты и запросы

- Пути и имена параметров объявляй в `ApiRoutes`; сервер регистрирует маршруты из этого объекта.
- HTTP-вызовы API реализуй в `OneBookApi`. Клиентские репозитории вызывают его методы и не дублируют URL и тела запросов.
- Идентификаторы в пути кодируй как отдельные сегменты через построители `ApiRoutes`, поисковые и другие query-параметры передавай средствами Ktor `parameter`.
- `OneBookApi` получает `HttpClient` и базовый URL извне. Вызывающая сторона выбирает движок, настраивает JSON ContentNegotiation, таймауты и владеет закрытием клиента.
- Каждый запрос должен завершаться исключением при HTTP 4xx/5xx независимо от настроек переданного клиента. Не превращай ошибки в успешный результат или пустой список.
- Аудио передаётся плееру через `audioUrl`; потоковое чтение, Range/HEAD и управление воспроизведением остаются у плеера и сервера.
- Кеширование и преобразование DTO остаются в `client/core/data`. Кеш позиции обновляется, а снимок библиотеки инвалидируется только после успешного изменения на сервере. Сохраняй существующие правила обработки сетевых ошибок, HTTP-ошибок и отмены.

## Порядок изменения API и проверки

1. Добавь или измени общие DTO, маршрут и метод `OneBookApi`.
2. Обнови обработчик сервера и клиентский репозиторий; при необходимости обнови DI и работу с кешем.
3. Для изменения поведения добавь или обнови проверки реального контракта: общие запросы против тестового сервера, сериализация, параметры и ошибки. При изменении построения URL проверь кириллицу и зарезервированные символы. В тестах допустимы независимые литералы путей и JSON для проверки внешнего контракта.
4. Обнови описание `shared` и таблицу API в `README.md`, если изменилось публичное поведение.

Для изменений кода API запускай целевые проверки из корня проекта:

```powershell
.\scripts\gradle.ps1 :shared:jvmTest :server:test :client:core:data:desktopTest :check
```

При изменении DI дополнительно запускай `:client:core:common:desktopTest`. При изменении зависимостей, таргетов или публичного API библиотеки проверяй сборку потребителей:

```powershell
.\scripts\gradle.ps1 :client:core:desktop:classes :client:core:mobile:assembleDebug
```

Для правок только документации запуск сборки не требуется. В отчёте о выполнении указывай фактически выполненные проверки и оставшиеся ограничения.
