# OneBook

OneBook — единое приложение для поиска, хранения и прослушивания аудиокниг. Проект состоит из сервера на Ktor и клиента на Compose Multiplatform для Android и Desktop.

## Возможности

- Поиск аудиокниг и просмотр информации о них.
- Добавление книг в личную библиотеку.
- Хранение аудиофайлов на сервере и их передача клиенту.
- Прослушивание аудиокниг с сохранением позиции воспроизведения.

В начальной версии каталог задаётся локальным JSON-файлом, а аудиофайлы размещаются в каталоге данных сервера. Внешние источники, загрузка файлов через API и офлайн-хранение на клиенте будут добавляться отдельно.

## Сервер

**Стек:** Kotlin, Ktor.

Сервер предоставляет API для работы с каталогом и библиотекой, обрабатывает запросы клиента и раздаёт аудиофайлы. Для воспроизведения и перемотки сервер должен поддерживать потоковую передачу и HTTP Range-запросы.

Базовая архитектура — модульный монолит с разделением ответственности:

- `api` — маршруты Ktor, преобразование доменных моделей в общие DTO, проверка входных данных и обработка ошибок.
- `application` — сценарии поиска, работы с библиотекой и получения аудио.
- `domain` — модели и интерфейсы репозиториев и файлового хранилища.
- `infrastructure` — реализации доступа к данным, файловому хранилищу и внешним источникам.

Бизнес-логика не зависит от Ktor и конкретного способа хранения данных. В начальной реализации метаданные и состояние прослушивания хранятся в JSON, аудио — в локальной файловой системе. База данных и авторизация могут быть добавлены за существующими интерфейсами.

План импорта внешних каталогов и основной архитектурный каркас описаны в [документе синхронизации провайдеров](docs/backend-catalog-sync.md). Для каждого портала предусмотрен собственный парсер за общим контрактом; подключение БД, расписания и конкретных порталов запланировано отдельными этапами.

Первый адаптер — `AknigaProvider` для akniga.org. [Описание парсера и тестовая лаборатория](docs/akniga-parser.md) содержат команды автономных тестов, разбора локального HTML и проверки реального сайта. Адаптер пока не подключён к рабочему каталогу сервера.

## Общая библиотека shared

`shared` — Kotlin Multiplatform-библиотека с Android- и JVM-таргетами. Сервер и `client/core/data` подключают её через `implementation(project(":shared"))`.

- `BookDto`, `PositionDto`, `ErrorDto` — общие сериализуемые модели запросов и ответов. `PositionDto` используется и для чтения, и для сохранения позиции.
- `ApiRoutes` — пути API, имена параметров и построение путей с кодированием идентификаторов. Сервер регистрирует маршруты из этого же объекта.
- `OneBookApi` — готовые HTTP-запросы проверки доступности, каталога, информации о книге, библиотеки и позиции. `audioUrl` возвращает адрес для потокового плеера.

`OneBookApi` получает настроенный `HttpClient` и базовый адрес сервера. Вызывающий код выбирает движок, устанавливает JSON ContentNegotiation и таймауты, а также закрывает клиент. Ответы 4xx и 5xx завершаются исключением. Кеширование и преобразование DTO в клиентские доменные модели находятся в `core/data`; серверная бизнес-логика остаётся в `server`.

```kotlin
val api = OneBookApi(httpClient, "http://127.0.0.1:8080")
val books: List<BookDto> = api.books("Толстой")
api.savePosition(books.first().id, PositionDto(positionMs = 1234))
```

Новые сетевые модели, пути и HTTP-запросы добавляются в `shared`, затем подключаются к серверным обработчикам и клиентским репозиториям.

Обязательные [правила работы с shared](AGENTS.md) описывают границы модуля, совместимость контрактов, порядок изменения API и необходимые проверки.

## Клиент

**Стек:** Kotlin, Compose Multiplatform, Ktor Client, Koin, Decompose.

**Платформы:** Android и Desktop.

Клиент строится на принципах Clean Architecture и MVVM. Две основные директории клиента — `core` и `feature`.

### Core

Общие слои выделены в отдельные Kotlin Multiplatform-модули:

- `domain` — доменные модели, интерфейсы репозиториев и `AudioPlayer`, сценарии каталога, поиска, библиотеки и прогресса. Зависит только от Kotlin и Coroutines; не содержит Compose, Ktor, Koin, Decompose или платформенных API.
- `data` — репозитории поверх `shared/OneBookApi`, SQLite-кеш запросов через SQLDelight, преобразование общих DTO в доменные модели, конфигурация Ktor Client и DI для данных. Реализует контракты `domain`.
- `ui` — переиспользуемые Compose-компоненты и UI-состояние списка книг. Зависит от `domain`; используется фичами.
- `common` — общая навигация Decompose, DI сценариев, `CommonAudioPlayer` и сборка общего DI-графа. Объединяет `data` и DI-модули фич через `createCommonGraph`.

Платформенные приложения самостоятельно компонуют интерфейс и передают общему графу адрес API, HTTP-движок, фабрику SQLite-кеша и фабрику движка воспроизведения:

- `mobile` — Android-приложение: точка входа, выбор OkHttp и `AndroidPlaybackEngine`, навигация и компоновка мобильного интерфейса, интеграция с Android API.
- `desktop` — Desktop-приложение: точка входа, выбор CIO и `DesktopPlaybackEngine`, навигация и компоновка окон и панелей, интеграция с Desktop API.

Оба модуля используют универсальные компоненты фич. Например, на Android каталог и плеер могут открываться отдельными экранами, а на Desktop отображаться одновременно в разных областях окна.

В `mobile` и `desktop` платформенный код разделён на пакеты `audio` (движок воспроизведения), `di` (подключение платформенных зависимостей к общему графу) и `ui` (компоновка интерфейса и превью). В корневом пакете Android остаются `OneBookApplication` и `MainActivity`, в корневом пакете Desktop — `Main.kt` с функцией `main`.

`CommonAudioPlayer` управляет единой сессией воспроизведения: открывает книги, восстанавливает позицию, сохраняет прогресс, обрабатывает переключение книг, паузу и перемотку. Он работает через `PlaybackEngine`; в `mobile` находится `AndroidPlaybackEngine` на Media3, в `desktop` — `DesktopPlaybackEngine` на JavaFX. Адаптеры знают только об аудиоисточнике и состоянии движка. Сессией владеет DI-контейнер; уничтожение отдельной ViewModel не освобождает общий плеер.

### Feature

Фичи — переиспользуемые UI-компоненты с ViewModel, состоянием и обработкой действий пользователя. Они не зависят от платформы и не определяют компоновку приложения целиком.

Начальные функциональные области:

- `catalog` — каталог и информация об аудиокнигах.
- `search` — поиск аудиокниг.
- `library` — личная библиотека.
- `player` — управление воспроизведением и отображение его состояния.

Каждая фича содержит:

- `presentation` — Compose UI, ViewModel, состояние и действия пользователя.
- `di` — регистрацию своей ViewModel в Koin.

Доменные сценарии находятся в `core/domain`, реализации доступа к данным — в `core/data`. ViewModel получает сценарии или доменный контракт `AudioPlayer` через конструктор. Фичи не обращаются к HTTP-клиенту, DTO или конкретным репозиториям и не зависят друг от друга. Общий список книг и его UI-состояние вынесены в `core/ui`.

Направление зависимостей:

```text
feature:*       → core:ui → core:domain
feature:*       → core:domain
core:data       → core:domain, shared
server          → shared
core:common     → feature:*, core:data, core:domain
mobile/desktop  → feature:*, core:common, core:domain
```

`domain` не зависит от остальных модулей проекта. Фичи зависят от `ui` и `domain`, поэтому общий DI-граф в `common` может подключать их без циклических зависимостей. `createCommonGraph` регистрирует данные, сценарии, общую сессию воспроизведения и все ViewModel. Платформенные точки входа выбирают движки и владеют созданным Koin-контейнером.

Фичи не зависят от `core/mobile` и `core/desktop`. Доступ к платформенным возможностям, включая воспроизведение аудио, предоставляется через интерфейсы и передаётся извне. Переходы между фичами передаются платформенному модулю через события или callbacks.

### Роли библиотек

- **Compose Multiplatform** — общий UI фич и платформенная компоновка интерфейса.
- **Ktor Client** — взаимодействие с серверным API.
- **Decompose** — навигация, жизненный цикл компонентов и сохранение состояния навигации. Компоненты Decompose управляют навигацией и жизненным циклом; ViewModel отвечает за состояние и логику представления.
- **Koin** — внедрение и сборка зависимостей на обеих платформах. Общие регистрации находятся в `core/data`, `core/common` и DI-модулях фич. Платформенные точки сборки выбирают HTTP-движок и адаптер воспроизведения.

Общие фичи получают зависимости через конструкторы и не обращаются к DI-контейнеру напрямую.

## Кодстайл

- В объявлениях и вызовах `@Composable`-функций каждый параметр и аргумент располагается на отдельной строке, даже если он единственный.
- Для каждой `@Composable`-функции должно быть превью с аннотацией `@Preview`. Превью использует тестовые данные и не требует сетевых запросов или реальных зависимостей приложения.
- Каждая ViewModel скрыта за интерфейсом: UI и другие потребители зависят от интерфейса, а конкретная реализация предоставляется через DI. Интерфейс описывает доступное состояние и действия пользователя; детали реализации остаются внутри класса ViewModel.
- Интерфейс и его реализация объявляются в разных файлах.
- Основная реализация ViewModel называется `<ИмяИнтерфейса>Impl` и находится в одноимённом файле: `CatalogViewModel.kt` и `CatalogViewModelImpl.kt`.
- Реализация объявляет собственный изменяемый поток непосредственно в переопределённом свойстве: `override val state = MutableStateFlow(BooksState())`, без отдельного `mutableState` и `asStateFlow()`. То же правило действует для `query`, `message` и других таких потоков. В интерфейсе остаётся тип `StateFlow`; передачу готового состояния зависимости, например `override val state = player.state`, сохраняем.

Реализации ViewModel имеют вид `internal class CatalogViewModelImpl : ViewModel(), CatalogViewModel`. Модуль фичи предоставляет платформе функцию получения интерфейса через `ViewModelStoreOwner`: экземпляр сохраняется в `ViewModelStore`, а его очистка отменяет `viewModelScope`. UI получает только интерфейс. Для превью используются заглушки интерфейсов; сами функции с `@Preview` не требуют дополнительных превью.

### Detekt

Detekt 1.23.8 проверяет Kotlin-исходники всех модулей клиента, сервера и общей библиотеки. Правила реализованы в `detekt-rules`, конфигурация находится в `config/detekt/detekt.yml`:

- `ComposableMultilineArguments` — каждый параметр объявления и аргумент вызова Composable на отдельной строке, закрывающая скобка также на отдельной строке. Завершающая лямбда может начинаться после скобки.
- `ComposablePreview` — для каждой Composable в том же файле есть функция с `@Preview` и `@Composable`, вызывающая этот компонент.
- `ViewModelInterface` — реализация ViewModel имеет видимость `internal` и реализует интерфейс.
- `InterfaceImplementationSeparation` — интерфейс и реализующий его класс находятся в разных файлах.
- `ViewModelImplementationNaming` — основная реализация ViewModel называется `<ИмяИнтерфейса>Impl`, файл называется так же, как класс.
- `DirectMutableStateFlow` — переопределённые свойства потоков используют `MutableStateFlow` напрямую, без приватного промежуточного потока или обёртки `asStateFlow()`.

Проверка выполняется без разрешения типов: Composable проекта индексируются автоматически по аннотациям, внешние Compose API перечислены в `ComposableMultilineArguments.externalFunctions`. При добавлении новых внешних Compose API расширяйте этот список в правиле или задавайте полный список через конфигурацию. Правило превью проверяет наличие вызова компонента; отсутствие сетевых обращений в превью проверяется при ревью.

```powershell
.\scripts\gradle.ps1 detekt
.\scripts\gradle.ps1 :check
```

`:check` запускает Detekt и тесты пользовательских правил. Нарушения завершают проверку с ошибкой; baseline и подавления для текущего кода не используются. Отчёты Detekt находятся в `build/reports/detekt/`.

## Запуск

Требуются JDK 21 и Android SDK 35 для Android-сборки. Укажите JDK 21 в `JAVA_HOME`, а путь к Android SDK — в `ANDROID_HOME` или в локальном `local.properties` (`sdk.dir=...`). В Android Studio откройте корневую директорию проекта и выберите JDK 21 для Gradle.

Версии зависимостей закреплены в `gradle/libs.versions.toml`: Kotlin 2.1.21, Compose Multiplatform 1.8.2, Ktor 3.1.3, Koin 4.0.4, Decompose 3.3.0. Gradle Wrapper включён в репозиторий.

Команды ниже приведены для PowerShell в корне проекта. На Linux/macOS используйте `./gradlew` вместо `.\gradlew.bat`.

Для Windows с кириллицей в пути пользователя предусмотрен `scripts/gradle.ps1`. Он выбирает установленный JDK 21 (из `JAVA_HOME`, Android Studio или кэша Gradle), использует короткие Windows-пути и временный каталог внутри проекта. В таком окружении заменяйте `.\gradlew.bat` на `.\scripts\gradle.ps1`, например:

```powershell
.\scripts\gradle.ps1 :server:test :client:core:data:desktopTest :client:core:common:desktopTest
```

Скрипт изменяет переменные окружения только на время запуска сборки.

### Сервер и аудиокниги

```powershell
.\gradlew.bat :server:run
```

По умолчанию сервер слушает `127.0.0.1:8080`. При первом запуске создаются `data/` и пустой `data/catalog.json`. Для добавления книг остановите сервер, заполните `data/catalog.json` по образцу `examples/catalog.json`, разместите аудиофайлы в `data/audio/` и перезапустите сервер. Значение `file` — путь относительно `data/`; выход за пределы этой директории запрещён.

Настройки сервера через переменные окружения:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `ONEBOOK_HOST` | `127.0.0.1` | Адрес прослушивания |
| `ONEBOOK_PORT` | `8080` | Порт HTTP |
| `ONEBOOK_DATA_DIR` | `data` | Каталог метаданных и аудиофайлов |

Библиотека и позиции прослушивания сохраняются в `data/listening.json` и переживают перезапуск сервера. Каталог читается при запуске.

### Desktop

В отдельном терминале:

```powershell
.\gradlew.bat :client:core:desktop:run
```

По умолчанию клиент подключается к `http://127.0.0.1:8080`. Другой адрес задаётся переменной `ONEBOOK_API_URL`. Каталог, поиск и библиотека отображаются в центральной области окна; плеер всегда доступен справа. Аудио воспроизводится через JavaFX Media; поддержка форматов зависит от ОС и установленных кодеков. Для начала используйте MP3.

### Android

```powershell
.\gradlew.bat :client:core:mobile:assembleDebug
```

Откройте модуль `client/core/mobile` в конфигурации запуска Android Studio или установите APK из `client/core/mobile/build/outputs/apk/debug/`. Debug-клиент использует `http://10.0.2.2:8080` — адрес компьютера из стандартного Android-эмулятора. Для физического устройства измените `API_URL` debug-сборки и настройте доступ к серверу. Release-адрес пока является заглушкой и должен быть заменён перед выпуском.

На Android фичи открываются отдельными экранами. Воспроизведение реализовано через Media3 ExoPlayer. При уходе приложения в фон воспроизведение приостанавливается; фоновый сервис и управление из уведомления пока не реализованы.

На обеих платформах позиция отправляется на сервер каждые пять секунд, при паузе и перемотке, а при открытии книги восстанавливается с сервера. Без доступного сервера воспроизведение и сохранение прогресса не гарантируются.

### Кеш запросов

Репозитории сначала обращаются к серверу. Успешно полученные каталог, результаты поиска, библиотека и позиции прослушивания записываются в SQLite через SQLDelight 2.1.0. При сетевой ошибке, таймауте или ответе 5xx возвращается последний сохранённый результат того же запроса. Кеш сохраняется после перезапуска приложения.

Каждый поисковый запрос и каждая книга для позиции имеют отдельный ключ; данные разных адресов API изолированы. Пустые списки тоже кешируются и заменяют предыдущий результат. Если сохранённых данных нет, запрос завершается исходной ошибкой. Ответы 4xx, некорректный JSON и отмена запроса не заменяются кешем.

На Android БД находится в приватном каталоге приложения под именем `requests.db`, на Desktop — в `${user.home}/.onebook/requests.db`. Работа с БД выполняется на `Dispatchers.IO`. Фабрику платформенного драйвера передаёт пакет `di`, кеш создаёт и закрывает общий DI-контейнер. Если запись в БД не удалась, успешный сетевой ответ остаётся доступен вызывающему коду.

Успешное сохранение позиции обновляет её кеш. После успешного добавления или удаления книги снимок библиотеки удаляется, а следующий успешный GET сохраняет актуальный список. Неудачная операция изменения данных не изменяет кеш и возвращает ошибку. Офлайн-очередь изменений и кеширование аудиофайлов не реализованы.

Серверные тесты проверяют поиск, библиотеку, сохранение позиции, HTTP Range/HEAD, неизвестные книги и недопустимые позиции, а также совместимость общих запросов и DTO с сервером. Тесты `shared` проверяют кодирование идентификаторов и ошибки HTTP-запросов. Тест `core/data` проверяет кодирование поискового запроса и преобразование ответа API в доменную модель. Тесты `core/common` проверяют восстановление прогресса, переключение книг, автосохранение, паузу, перемотку, обработку ошибок, отмену и освобождение движка.

## API начальной версии

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/health` | Проверка доступности |
| `GET` | `/api/books?q=...` | Каталог и поиск по названию или автору |
| `GET` | `/api/books/{id}` | Информация о книге |
| `GET`, `HEAD` | `/api/books/{id}/audio` | Аудиофайл, включая HTTP Range |
| `GET` | `/api/library` | Книги в библиотеке |
| `PUT`, `DELETE` | `/api/library/{id}` | Добавление и удаление из библиотеки |
| `GET` | `/api/books/{id}/position` | Позиция прослушивания |
| `PUT` | `/api/books/{id}/position` | Сохранение JSON `{"positionMs": 1234}` |

Начальная версия рассчитана на одного пользователя и один процесс сервера. Авторизация, разделение данных по пользователям, внешние каталоги, главы и скачивание для офлайн-прослушивания пока не реализованы. По умолчанию сервер доступен только локально; перед публикацией необходимы авторизация и HTTPS.
